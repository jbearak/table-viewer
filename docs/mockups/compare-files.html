4 · The compare window

One grid, not two panes — the unified view the existing engine already produces. Title is old ↔ new. A header strip names both sides with the diff colors they own; a Read-only pill states why nothing is editable. Deleted rows keep the original's content, struck through; changed cells show before after; changed column headers get an accent underline; sheet tabs carry added/deleted badges.

5 · Aligning, before any rows are shown

The alignment pass is not an optimisation — it is what makes the diff correct. Comparing row N to row N (what the Git path does today) reports every row below an inserted one as changed, so no rows are shown until the two sides have been aligned. The window opens immediately into this state, with a Cancel that closes it.

6 · When the files will not align

Two unrelated or fully re-sorted files make any content diff degenerate. The alignment stops after a bounded effort and falls back to comparing row N against row N — the grid is still shown, but the banner states plainly that the rows could not be matched up, so an all-changed grid is never mistaken for a real result.

8 · What is deliberately absent

No side-by-side split, no edit affordances, no Save. The window refuses edits at the host level, not just in the UI — the same guard the Git compare panel already uses. There is no “show changes” toggle: in a compare window the diff is the document, and switching it off would just show the modified file — which plain Open already does. “Only changed rows” and the change counts are the two genuinely new pieces of the viewer surface; the paint rules in mockup 4 are already implemented for Git diffs. The row alignment, however, is new: the Git path compares row N to row N, which is adequate for in-place working-tree edits and wrong for two arbitrary files.
